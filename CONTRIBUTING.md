# Как поучаствовать

Проект открыт для правок. Ниже — то, что нужно знать до первой отправки.

*English: this file is in Russian; issues and pull requests in English are welcome too.*

## С чего начать

- **Нашли ошибку** — заведите [issue](https://github.com/Regsorm/code-index-mcp/issues)
  и приложите: версию (`code-index --version`), операционную систему, язык
  индексируемого репозитория, вызов инструмента с параметрами и полученный ответ.
  Для проблем с индексацией полезен кусок журнала демона.
- **Есть предложение** — заведите issue или тему в
  [Discussions](https://github.com/Regsorm/code-index-mcp/discussions).
  Крупную работу лучше обсудить до того, как она написана.
- **Вопрос по работе** — Discussions. Ответ там останется другим.

## Сборка

Нужен Rust 1.77 или новее.

```bash
cargo build --workspace                                      # проверка сборки
cargo build --release -p code-index                          # бинарник без 1С
cargo build --release -p bsl-indexer --features enrichment   # бинарник с поддержкой 1С
```

Состав рабочего пространства:

| Крейт | Что внутри |
|---|---|
| `crates/code-index-core` | парсер, индексатор, хранилище, демон, слой MCP, кэш, федерация |
| `crates/code-index` | публичный бинарник без 1С |
| `crates/bsl-extension` | разбор метаданных 1С и инструменты для них |
| `crates/bsl-indexer` | бинарник с поддержкой 1С |
| `crates/bsl-parse` | вспомогательный разбор BSL |

## Тесты

```bash
cargo test --workspace --all-targets
```

Прогоняйте по всему рабочему пространству, а не по одному крейту: правка в ядре
почти всегда задевает тесты расширений. Правка, ломающая тесты, не принимается.

Тесты, требующие индекса, создают его во временном каталоге через `tempfile` —
рабочие базы для проверки не нужны.

## Правка

- Правьте только то, что относится к задаче. Попутный рефакторинг работающего
  кода, переформатирование и «заодно причесал» затрудняют разбор правки.
- Держитесь стиля соседнего кода: комментарии в этом проекте на русском,
  сообщения об ошибках — тоже.
- Поведение, видимое пользователю, описывается в обоих журналах изменений —
  `CHANGELOG.md` и `CHANGELOG_EN.md` — с одинаковым смыслом. Исправление
  внутренней ошибки достаточно описать в журналах; новая возможность требует
  ещё и строки в README (`README.md`, `README_RU.md`, `README_EN.md`).
- Новый язык или новый инструмент MCP — заранее опишите замысел в issue:
  у части решений есть причины, не видные из кода.

## Что не принимается

- Учётные данные, токены, ключи, внутренние адреса и пути конкретных машин в
  любом виде, включая примеры конфигурации и тексты тестов.
- Названия заказчиков и конкретных внедрений в примерах. Типовые конфигурации
  называть можно («Управление Торговлей», «Бухгалтерия предприятия»), связку с
  заказчиком — нет.
- Файлы из `target/`, `.code-index/` и прочие следы сборки и работы индекса.

## Оформление правки

- Отдельная ветка на одну задачу, отдельный коммит на одну смысловую перемену.
- Заголовок коммита — вида `fix: …`, `feat: …`, `docs: …`, `perf: …`, дальше
  краткое описание сути.
- В описании запроса на слияние: что было не так, что стало, чем проверено.
