# ТЗ: обрезка по размеру не должна уносить список найденного

Дата постановки: 15.08.2026. Источник — разбор прогона `agents-mcp` (задача
`КлиентыЖТ_СкидкаНаЖТ`), где планировщик сжёг весь лимит ходов и не выдал план.

## 1. Что происходит сейчас

Вызов поиска по подстроке имени:

```
get_object_structure(repo="ut", name_like="Соглашения", sections=["attributes"])
```

Ответ:

```json
{"result": {"matched": 38, "results_count": 38, "results_omitted": true, "truncated": false}}
```

Тридцать восемь объектов найдено, **список имён не отдан ни одним элементом**.
Клиент получает три числа. Нужный объект (`Catalog.СоглашенияСКлиентами`) был
среди них.

### Замер, объясняющий поведение

| Составляющая ответа | Байт |
|---|---|
| секции `attributes` 38 объектов | 34 311 |
| имена, типы, синонимы | 7 190 |
| обрамление: счётчики секций, ключи JSON на объект | ~5 000 |
| **итого** | **≈ 46–47 тысяч** |
| бюджет `[cap].max_response_bytes` (дефолт) | 48 000 |

Превышение — единицы процентов. Потеря — стопроцентная.

Перекрёстная проверка: соседний вызов `name_like="СоглашенияС"` (25 объектов,
причём со **всеми** секциями, ~40 тысяч байт) отдался целиком, нужный справочник
шёл первым в списке. Разница между «всё» и «ничего» — около 7 КБ, то есть 15 %.

### Причина в коде

`crates/code-index-core/src/mcp/cap.rs`, `omit_oversize_sections`: пока
сериализованный размер больше бюджета — ищется **самая тяжёлая секция
(массив/мапа) и выбрасывается целиком**, вместо неё кладутся `<ключ>_omitted` и
`<ключ>_count`.

Для структуры одного объекта правило верное: выкинуть сотни значений
перечисления, оставив паспорт объекта. Но в ответе на поиск самая тяжёлая
секция — это внешний массив `results`, других претендентов рядом нет. Он и
вылетает первым же шагом, вместе со всеми именами. Внутрь элементов алгоритм не
заходит.

### Почему `sections=[]` не спасает

`crates/bsl-extension/src/tools/get_object_structure.rs`, `apply_sections`:
фильтр применяется только при `!secs.is_empty()`. Пустой список означает «все
секции» ради обратной совместимости — это закреплено тестом
`apply_sections_filters_top_level_keys`. То есть у клиента **нет** способа
попросить «только имена».

### Цена дефекта на живом прогоне

Планировщик `agents-mcp` (локальная модель Qwen3.8-27B) получил три числа,
не понял, что объекты есть, и потратил все 14 ходов на перебор `metaType`
вслепую. Задача корпуса провалена на первом же шаге. Сильная модель, возможно,
догадалась бы сузить критерий; слабая — не догадалась.

## 2. Что требуется

### Требование 1 (главное). Опознание объекта неприкосновенно

При любом превышении бюджета в ответе на поиск (`name_like`, `full_names`)
каждый найденный элемент обязан сохранить `full_name`, `meta_type`, `name`,
`synonym`. Выбрасываются **тяжёлые секции внутри элементов**, а не сам массив.

Порядок деградации — сверху вниз, следующий шаг только если предыдущего не
хватило:

1. снять тяжёлые секции внутри элементов (`attributes`, `tabular_sections`,
   `enum_values`, …), пометив каждый `<секция>_omitted` + `<секция>_count`;
2. если всё ещё не влезает — сократить сам массив, оставив первые N элементов и
   выставив `results_total` (сколько найдено) и `results_shown` (сколько отдано);
3. массив не обнулять никогда: при любом бюджете отдать хотя бы один элемент.

Контрольный расчёт по случаю выше: одни имена весят 7190 байт — седьмая часть
бюджета. Шага 2 не потребовалось бы.

### Требование 2. Параметр бюджета на вызов

Необязательный параметр `max_response_bytes` (целое) у структурных инструментов:
перекрывает глобальный `[cap].max_response_bytes` для одного вызова.

- потолок задаётся на сервере (`[cap].max_response_bytes_hard`, дефолт — скажем,
  4× обычного бюджета). Запрос сверх потолка не отклоняется, а зажимается до
  потолка, и это отражается в ответе;
- применённое значение возвращается в ответе полем `response_budget_applied`;
- значение `0` (снять страж) на вызов **не** разрешать: снимать страж можно
  только конфигом сервера.

Обоснование потолка: неограниченный ответ рвёт контекст самого клиента. В том же
прогоне 15.08 генератор уже падал с `request (261008 tokens) exceeds the
available context size (131072)`.

### Требование 3. Подсказка называет ручку и цену

Сейчас текст при обрезке советует `grep_code`/`grep_body` — инструменты, которых
у вызывающего агента может не быть в разрешённых, и не называет ни фактического
размера, ни имени параметра.

Требуется: указать, сколько весил бы полный ответ, и обе доступные меры —
например «полный ответ 63 КБ при бюджете 48 КБ; повторите с
`max_response_bytes=64000` либо сузьте `name_like`». Формулировка — на усмотрение
реализации, обязательны два числа и имя параметра.

### Требование 4. Явный режим «только имена»

`sections=[]` сегодня означает «все секции», и менять это нельзя — обратная
совместимость. Нужен отдельный вход: параметр `names_only: true` (либо
`sections=["none"]`) — вернуть только `full_name`, `meta_type`, `name`,
`synonym`, без структуры.

Это дешёвый режим поиска: на разобранном случае 38 объектов уложились бы в 9,5 КБ
вместо 63 КБ.

## 3. Проверка приёмки

Все пункты — на живом сервере, репозиторий `ut`, дефолтный бюджет.

1. `get_object_structure(repo="ut", name_like="Соглашения", sections=["attributes"])`
   → в ответе **38 элементов**, у каждого заполнены `full_name` и `meta_type`;
   `Catalog.СоглашенияСКлиентами` присутствует. Секции при необходимости
   помечены `attributes_omitted` + `attributes_count`.
2. Тот же вызов с `names_only=true` → 38 элементов без структуры, размер ответа
   меньше 12 КБ.
3. Тот же вызов с `max_response_bytes=70000` → полные секции, поле
   `response_budget_applied` = 70000.
4. Запрос `max_response_bytes` заведомо выше потолка → ответ приходит, бюджет
   зажат до потолка, `response_budget_applied` равен потолку.
5. Искусственный набор, где даже имена не влезают в бюджет → отдан хотя бы один
   элемент, выставлены `results_total` и `results_shown`, `results_omitted`
   не выставлен.
6. Структура **одного** объекта с сотнями значений перечисления → поведение как
   прежде: тяжёлая секция опущена целиком с `_count`, паспорт объекта на месте.
   Правка не должна ломать этот случай.
7. Юнит-тесты на `omit_oversize_sections`: массив результатов не выбрасывается
   целиком ни при каком бюджете больше нуля.

## 4. Чего делать не надо

- Не поднимать дефолтный `max_response_bytes`: это лечит симптом и бьёт по
  контексту всех клиентов.
- Не трогать сессионный дедуп (`serve_dedup.rs`, `rows_elided_already_delivered`):
  это другой механизм, к разобранному случаю отношения не имеет — проверено, у
  ответа стоял маркер `response_sections_omitted`, а сам случай воспроизводится
  на первом обращении к репозиторию в свежей сессии.
- Не менять смысл `sections=[]` — сломает обратную совместимость.

## 5. Порядок выкатки

Проект имеет полный релизный цикл, срезать нельзя: тесты workspace → локальная
сборка и деплой через mcp-supervisor → локальный smoke на живой базе →
musl-сборка → раскатка на ВМ (репозитории `ut`, `bp-ss`, `bp-tdk`, `zup` живут
там) → федеративный smoke → аудит секретов → коммит. Пункт 1 проверки приёмки
идёт по федеративному пути: `ut` обслуживается удалённым узлом.
